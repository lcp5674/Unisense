# Unisense 指标产品多角色优化分析

- **生成日期**：2026-08-21
- **分析对象**：指标语义平台（指标域全生命周期：建指标 → 找指标 → 管指标 → 用指标）
- **分析方式**：从产品经理、管理者/业务老板、数仓/数据架构师、技术/工程、业务用户五类角色视角，各自只看自己真正关心、能拍板的事
- **用途**：作为后续产品迭代排期与跨角色对齐的依据，便于查询与比对

---

## 0. 分析基线（已达成高地，避免重复建议）

- 14 领域服务 released，指标 OneData 重构（逻辑度量目录 `measure_catalog` + 挂载 `metric_mount`）已落地（Phase 1-4）
- 血缘企业级 P0-P5 全部完成（评测集 504 条、parse-batch、健康度、路径/断链、OpenLineage 导出、Hive 宏展开、DDL 血缘、库级扫描、定时调度）
- 采集工业级（HMS 直连/库表级联/限流）、治理 97 按钮级权限点、敏感规则可视化配置台、可观测企业级概览、通知业务化

## 1. 产品经理视角：业务方找得到、看得懂、用得上指标

| 优化点 | 说明 | 优先级 |
|---|---|---|
| **找指标要"说人话"** | 当前仅关键词精确匹配——业务搜"住院费"找不到正式名"住院医疗费用"。需支持同义表达、联想推荐，让不懂命名规范的业务用户也能搜到 | P0 |
| **口径要"看得懂"** | 口径散落在技术字段，业务看不懂。需一张"业务口径卡"：怎么算、口径是什么、谁定义的、何时改过——一句话讲清 | P0 |
| **详情页要"让人信"** | 打开指标第一眼可见：状态、最近一次校验通过时间、质量分、被多少报表引用。把治理结果转译成业务信任 | P1 |
| **从"看指标"到"用指标"** | 指标详情页一键"试算/下推出数"，业务当场验证口径，不必回 BI 试半天 | P1 |
| **存量指标批量迁移** | 存量 atomic 现靠"人工重建引导"，四位数规模不可扩展。做半自动迁移向导：旧指标 → 自动生成逻辑度量+挂载，人工只确认语义归属 | P1 |
| **质疑闭环** | 业务对口径有疑问时一键"质疑"，走 质疑→澄清→修订 闭环，而非私下扯皮 | P2 |

## 2. 管理者 / 业务老板视角（刻意不用技术语言）

**关心：钱、风险、信任、效率。以下全部用业务语言表述。**

### 2.1 "我们的数能不能信"——决策底线（P0）
老板拿指标开经营会最怕两件事：口径对不上、数据对不上。需要一个**指标可信度仪表盘**：把关键指标标成红/黄/绿，一眼看出"哪些数现在能放心用、哪些在亮红灯"。不是技术健康度，是业务可信度。

### 2.2 "指标资产到底值不值钱"——投入产出账（P1）
建了几千个指标，真正在用的有多少？没人用的指标是沉没成本，重复建设是浪费。需要一张**指标资产账本**：活跃使用 / 僵尸指标 / 重复建设清单。这是最能打动老板的一张报表——直接回答"投入花得值不值"。

### 2.3 "部门之间别扯口径了"——全公司一个口径（P1）
营收、毛利、客户数，销售一套、财务一套，是跨部门扯皮常见根源。平台核心价值即"一个口径、全公司统一"。要能**量化**：口径一致率、口径争议平均解决时长，让老板看到平台在减少内耗。

### 2.4 "数据安全会不会出事"——合规底线（P1）
医疗/金融场景，敏感数据泄露是事故级风险。需**一键出合规报告**：哪些敏感指标被谁访问过、导出记录、审计留痕。老板不关心实现，只关心"能否向监管/客户证明合规"——这是私有化投标/验收的硬材料。

### 2.5 "业务问个数要多久"——响应时效（P1）
业务提一个数据需求，现在要几天？上线后目标几小时？这是老板能直接感知的 KPI，也是平台价值的终极证明。

### 2.6 "上生产有没有风险"——用业务语言说风险（P0）
- 核心能力（指标口径"唯一真相源"）**还没完成最终验收**——最核心的地基还没盖章；
- 大规模数据量下的性能**还没在真实环境压测过**——万一上线首日业务侧卡顿，责任归属要提前说清。

## 3. 数仓 / 数据架构师视角：口径治理与资产复用

| 优化点 | 说明 | 优先级 |
|---|---|---|
| **指标复用度分析** | 原子→派生→报表引用链统计，识别"重复建设"与"无人使用"。OneData 价值是"一处定义、多处复用"，没有复用度报表，价值无法量化 | **P0** |
| **数值正确性对账** | 现质量卡在"结构"层（字段齐不齐、SLA），数仓最痛的是"口径写对了、算出来是错的"。对关键 Tier-1 指标做抽样对账：下推跑口径 SQL vs 源表聚合，差异报警 | P1 |
| **源表变更→指标影响闭环** | 源表下线/字段变更 → 自动标记受影响指标 → 通知 Owner。各环节单独已通，整条链路需端到端验收 | P1 |
| **命名规范强约束** | 发布指标必须过词根校验（服务端硬卡），防止命名规范随指标规模崩塌 | P1 |
| **口径术语库** | 把指标口径"字典化"，所有人对同一口径说同一种话，支撑"口径一致率"量化 | P1 |
| **僵尸指标下线流程** | 明确下线审批与影响检查，防止误删被引用指标 | P2 |

## 4. 技术 / 工程视角：指标域工程质量

| 优化点 | 说明 | 优先级 |
|---|---|---|
| **semantic 模块定稿** | 指标语义真相源（口径状态机、Owner 门禁、级联）是唯一停在 implemented 的核心模块——指标域"心脏"未 released | **P0** |
| **检索架构升级** | 指标/表检索现为数据库模糊匹配（MySQL LIKE），10 万表规模是确定性能瓶颈；ES 服务已部署未启用，需选型落地 | **P0** |
| **指标计算链路性能** | 大查询下推 Doris/StarRocks、热点指标 Cube 预聚合，避免业务查询拖垮主库 | P1 |
| **权限与安全测试覆盖** | 行级隔离/跨域门禁近期经历一次"半成品移除"险情，需系统化测试覆盖防回归 | P1 |
| **指标版本快照** | 口径变更可追溯、可回滚，变更历史完整可查（配合产品视角"口径卡"） | P1 |
| **前端测试质量** | 指标注册页存在测试与组件失配问题，测试应改为"按用户行为断言"，而非跟随组件实现补丁 | P2 |

## 5. 业务用户视角（横向补充）

- **指标可信度可视化**：详情页已有状态/健康度，但"最近一次校验通过时间、质量分、被多少报表引用"应一眼可见——把治理结果转译成业务信任。
- **变更订阅闭环**：通知已业务化，但"订阅某指标口径变更/源表下线"的**用户主动订阅**能力值得补强（当前偏系统推送）。

## 6. 跨角色优先级排期（未来 3-6 个月）

| 优先级 | 事项 | 主要受益角色 |
|---|---|---|
| **P0** | semantic 定稿（业务语言：给"口径唯一真相源"盖章） | 管理+技术 |
| **P0** | 找指标从"精确匹配"变"说人话"（同义/联想检索） | 产品+业务 |
| **P0** | 指标可信度仪表盘（红黄绿） | 管理者+数仓 |
| **P0** | 性能实证 + 上生产风险报告（k6 live 复测） | 管理者+技术 |
| **P1** | 指标资产账本（活跃/僵尸/重复建设） | 管理者+数仓 |
| **P1** | 存量指标批量迁移向导 | 产品+数仓 |
| **P1** | 数值对账（口径对但算错） | 数仓 |
| **P1** | 源表变更→指标影响闭环端到端验收 | 数仓+技术 |
| **P1** | 合规一键报告 | 管理者 |
| **P2** | 质疑闭环、口径术语库、Cube 预聚合、AI 消费引导、前端测试重构 | 全角色 |

---

## 7. 一句话总结

指标的功能面已非常完整，当前最大杠杆不在"再加功能"，而在**把"可信"与"资产价值"量化出来给决策者看**：产品补齐"说人话的检索 + 看得懂的口径卡"，管理者拿到"红黄绿仪表盘 + 资产账本"，数仓拿到"复用度 + 数值对账"，技术把核心模块盖章（semantic 定稿 + 性能实证）。每个角色都有一件自己能拍板、能看见结果的事。
