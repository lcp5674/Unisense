# ADR-002: 血缘解析采用 sqlglot 纯函数 + MySQL 权威存储 / Neo4j 可选可视化分层

## 状态：Accepted
## 日期：2026-08-08
## 背景
需解析 SQL 得到表级/字段级血缘并支持影响分析（TD §12.2）。核心挑战：
1. 解析引擎选型：需可控、可单测、不依赖外部服务；
2. 存储选型：图遍历性能 vs 权威一致性；
3. 图数据库（Neo4j）可用性不应拖垮核心血缘入库链路。

对应模块 `lineage`（状态 released，13/13 门禁）。

## 决策
1. **解析用 sqlglot 纯函数**：`extract_table_lineage` / `extract_field_lineage` 均为纯函数，不依赖 DB/网络，便于单测穷举。字段级采用**投影级映射**（`SELECT <src> AS <tgt>`），因 sqlglot 30.x 移除 `LineageRunner` / `Scope.column_lineage` 高列级 API；链式 CTE/子查询的深度解析由后续血缘通道（调度日志/运行日志/LLM 补位）补全。
2. **存储分层**：MySQL 为**权威边存储**（表边/字段边落库）；Neo4j 仅为图可视化与遍历的**可选依赖**。`LineageGraphClient.write_edges` 采用 best-effort 降级（未配置/驱动缺失/不可达均返回 `False`），不阻断主流程。
3. **影响分析约束**：BFS 每跳每方向受 `max_hops≤10` 与 `max_edges≤5000` 双重约束，抑制 N+1 往返放大。

## 备选方案
- **纯 Neo4j 存储**：图遍历强，但引入强依赖且双写一致性难保，Neo4j 宕机拖垮入库 → 否决。
- **LLM 解析血缘**：成本高、不可控、难单测、不可穷举 → 否决。
- **不区分可选/权威依赖**：Neo4j 故障即整体降级 → 否决。

## 后果
- **正面**：核心链路仅依赖 MySQL，Neo4j 宕机不影响血缘入库；解析层可穷举单测；影响分析有界。
- **负面**：字段级血缘为基线粒度（投影级），深度列血缘待补全；影响分析每跳每方向一次 DB 往返（受 `max_edges` 约束缓解）；别名归一化需 `_build_alias_map` 保证字段图与表图连通（已实现）。
