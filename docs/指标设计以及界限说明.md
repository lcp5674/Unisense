# 指标设计以及界限说明

## 概览

本文档用于明确指标平台/数仓指标体系中 **原子指标、派生指标、复合指标** 的定义、设计原则与界限。先说明"怎么设计"，再说明"怎么分层"，统一指标资产的建设口径，避免口径不统一、指标重复建设与层级误用。

- 适用读者：数仓开发、指标平台研发、数据产品
- 遵循方法论：OneData（原子 = 统计口径 + 算法抽象；派生 = 统计周期 + 原子 + 业务限定；复合 = 派生公式组合）
- 口径出处：AGENTS.md 第 8 节、`docs/指标平台需求规格说明书_v2.0.md` 5.3/5.4/5.5、`output/kb/index/02_原子指标.yaml` / `03_派生指标.yaml` / `04_复合指标.yaml`

## 1. 三层指标定义与设计原则

### 1.1 定义

| 层次 | 定义 | 构成要素 | 典型示例 |
|---|---|---|---|
| 原子指标 | 统计口径 + 算法抽象，不绑定业务场景和物理表 | 聚合函数/算法、数据类型、度量单位、可累加性（含半累加/窗口取值）、时间标识 | 费用求和（`settle_amt`）、发生金额求和（`occur_amt`） |
| 派生指标 | 依赖指标（原子或派生）+ 业务限定 + 统计周期 + 衍生逻辑（按指标类型），不加统计粒度 | 依赖指标、指标类型、业务限定、统计周期、衍生逻辑 | 门特-癌症-发生金额（`special_cancer_occur_amt`） |
| 复合指标 | 多个派生指标的公式组合（比率/占比/差值） | 公式、依赖派生指标 | 结余率（`surplus_rate`） |

### 1.2 设计原则

**原子指标**

- 统计口径 + 算法抽象，不绑定业务场景和物理表
- 英文名称小写+下划线、全局唯一；同算法跨表复用，不重复新增
- 可累加性（含半累加/窗口取值）、时间标识等固有属性在原子层声明

**派生指标**

- 统计周期 + 原子指标 + 业务限定，不加统计粒度
- 英文名称 = 业务限定前缀 + 原子英文名
- 挂载数据集必填；统计粒度由挂载表/数据集决定，不进入指标定义

**复合指标**

- 多个派生指标的公式组合（比率/占比/差值）
- 公式仅引用派生指标英文名称与四则运算/括号，禁止裸表字段
- 依赖派生指标必填，且与公式实际引用保持一致

## 2. 原子指标设计

原子指标按**配置分层**组织，共三层：**基础信息（口径层）**、**计算口径（算法层）** 与 **业务信息（治理层）**。三层同属指标资产，都必须维护，禁止只维护其中一层。

### 2.1 基础信息——口径层

纯业务语义，与物理实现无关，不绑定物理表。回答"这个指标在业务上算什么"。

基础信息层暂定 9 项配置信息，规格如下：

| 配置项 | 必填 | 配置说明                                                       | 填写规范 | 示例                                           |
|---|---|------------------------------------------------------------|---|----------------------------------------------|
| 英文名称 | 是 | 原子指标的唯一业务标识，全局命名空间唯一，是派生/复合指标引用和查询消费（API/SQL）的键，属于口径层的命名要素 | 字符串 3~64 位；仅小写字母、数字、下划线，首字符为字母（正则 `^[a-z][a-z0-9_]{2,63}$`）；全局唯一；结构 = 度量主题 + 度量词后缀（`_amt`/`_cnt`/`_qty`/`_days`）；词根化、去表化（结算口径金额除外，统一 `_settle_amt` 后缀）；一经发布不可修改 | `settle_amt`、`patient_cnt`、`latest_blood_sugar` |
| 数据域 | 是 | 指标归属的分析主题域，以数据域编号为存储键、名称为展示值                               | 编号枚举 DOM-001~010，来自 `01_主题域.yaml`；名称由编号自动带出、只读；一个指标只能归属一个主题域 | 编号 `DOM-006` → 结算费用域                         |
| 中文名称 | 是 | 业务可读主名称，供业务方检索、展示与评审使用                                     | 支持任意字符；同主题域内不重复；业务可读、不写表名/字段名；与英文名称一一对应，不与同义词重复 | 结算金额、最新血糖检测值                                 |
| 度量格式 | 是 | 指标数值的展示类别，决定单位下拉与默认值 | 枚举：金额 / 比率 / 数值，三选一；金额→货币单位、比率→比例单位、数值→自定义单位 | 金额、比率、数值 |
| 度量单位 | 是 | 指标数值的计量单位，与度量格式配套 | 金额：分/元/万元/百万元/千万元/亿元/自定义，默认元；比率：小数/百分位数/千分位数/自定义，默认小数；数值：自定义为主（如 mmol/L、个、千克、次、人），默认无 | 元、小数、mmol/L |
| 小数位数 | 金额/比率必填 | 指标数值的展示精度 | 整数；与挂载表字段 scale 一致，避免展示截断或补零；默认值：金额 2、比率 4、数值不强制（按需） | 金额 2；比率 4；数值按需 |
| 源头系统 | 否（建议填） | 指标数据的来源业务系统，属业务溯源信息，辅助口径评审（不同 HIS 系统同名字段口径常有差异）            | 多系统用英文逗号分隔；填业务系统名（银海his、天信his、事前事中his审核、结算平台），不填物理表名；与算法层来源表/来源数据源区分 | 银海his,天信his,事前事中his审核                        |
| 同义词 | 否 | 指标的业务别名集合，供检索匹配                                            | 逗号分隔，中英文均可；覆盖口径文档、业务系统、历史报表的常见叫法；不含物理表名；与中文名称不重复 | 总费用,医疗金额,总金额                                 |
| 指标描述 | 否 | 一句话对口径进行精准描述，供检索匹配                                         | 文本 ≤200 字；只写用途与场景，不重复口径定义、不写 SQL/表名 | 患者就医后产生的结算流水金额                               |

> 注 1：源头系统按"业务溯源字段"保留在基础信息层；规格书 v2.0 5.3.5 将其归入"物理参考信息（规划下沉）"，最终定性待确认。
>
> 注 2：业务实体暂未纳入基础信息层，规划归属待定；可累加性由"累加类型"承载、时间标识由"时间字段"承载。指标描述（用途补充）归基础信息层；口径配置保留"业务口径"（口径定义），"指标口径"字段已废弃。

### 2.2 计算口径——算法层

聚合函数、来源表、计算字段等信息，是算法的实现。回答"这个指标怎么算出来"。

口径配置项：

| 配置项 | 必填 | 配置说明 | 填写规范 | 示例                                                                            |
|---|---|---|---|-------------------------------------------------------------------------------|
| 来源数据源 | 是 | 算法取数的业务数据源 | 填数据源标识（银海his、天信his、结算平台等） | 银海his                                                                         |
| 来源表 | 是 | 算法取数的明细表 | 默认 dw/dwd 明细层，不绑 dws 聚合表 | wedw_dw.jkda_dzbl_health_indicator_df                                         |
| 业务口径 | 否（建议填） | 一句话业务口径（口径定义） | 不含表名/物理字段名；四方评审必读字段；"指标口径"字段已废弃，以本字段为准 | 按就诊号去重统计的就诊次数                                                        |
| 计算逻辑 | 是 | 算法的实现方式 | 标准模式：选择来源表字段 + 聚合函数（sum/max/min/count/count_distinct/avg/first_value/last_value）；自定义模式：输入伪 SQL 计算口径；选择 first_value/last_value 时时间字段必填（排序基准） | 标准模式：last_value(blood_sugar)                                                  |
| 累加类型 | 是 | 累加：跨任意维度组合聚合后相加都有业务含义；半累加：部分维度可累加、另一部分维度不可累加；不可累加：任何维度都无法累加 | 枚举：可累加/半累加/不可累加；半累加时须配置不可累加维度（如时间）；去重计数默认不可累加，带时间窗口取值语义时才用半累加 | 半累加；不可累加维度=时间                                                                 |
| 过滤条件 | 否 | 数据有效性排除 | 只放数据有效性排除（blood_sugar!=0、状态=成功），业务限定放派生层 | blood_sugar != 0                                                              |
| 分析维度 | 否 | 允许下钻的公共维度 | 与来源表关联推导（来源表为根，left join 两层内维度） | 机构,病种,患者                                                                      |
| 技术口径(源业务库口径) | 否 | 开发提供的源业务库口径 SQL | 技术实现说明，可含表与字段，与指标口径分离 | select sum(amount) from med_risk.public.record_settle_bill where is_deleted=0 |

说明：来源主表等物理实现信息在规格书 v2.0 5.3.5 中列为"规划下沉至派生/挂载表"；本文按算法层保留来源表、计算字段等作为算法实现要素，最终落库口径以规格书附录 E 对齐为准。累加类型（可累加性）与时间字段（指标时间标识）均由本层承载。

### 2.3 业务信息——治理层

指标归属与生命周期治理信息，与口径层/算法层分离。

| 配置项 | 必填 | 配置说明 | 填写规范 |
|---|---|---|---|
| 创建人 | 是 | 指标录入人员 | 记录指标录入者；系统自动带出当前登录人，不可手动修改 |
| 业务负责人 | 是 | 业务方 | 指标口径变更的评审联系人，负责业务口径确认 |
| 产品负责人 | 是 | 产品经理 | 与业务负责人共同参与口径变更评审 |
| 技术口径负责人 | 是 | 业务开发，即提供技术口径（源业务库口径 SQL）的开发人员 | 负责 2.2 节"技术口径(源业务库口径)"的正确性与后续维护 |
| 状态 | 是 | 指标生命周期状态 | 枚举：新建 / 已发布 / 已修改 / 已下线；默认新建 |
| 术语标签 | 否 | 数据资产类标签 | 下拉多选，仅可选术语类型为"资产标签"的术语（按 `08_术语类型.yaml` 过滤 `07_业务术语.yaml`）；无资产标签术语时显示空态提示 |

> 注 3：状态枚举已统一为 4 态（新建/已发布/已修改/已下线），规格书 v2.0 5.3.4/5.4.1 已同步。
>
> **平台扩展态说明（Unisense 实现）**：生产平台在 4 态基础上保留扩展状态机
> `DRAFT → REVIEW → PUBLISHED → EXPERIMENTAL/DEPRECATED → DATA_SOURCE_DROPPED`，
> 以满足生产治理能力：`REVIEW`（评审中）、`EXPERIMENTAL`（灰度试用）、
> `DATA_SOURCE_DROPPED`（源表下线联动，自动标记而非静默失效）。文档 4 态与平台
> 扩展态一一对应：新建≈DRAFT、已发布≈PUBLISHED、已修改≈REVIEW/EXPERIMENTAL、
> 已下线≈DEPRECATED/DATA_SOURCE_DROPPED。**口径三层归属与生命周期语义不变**，
> 仅平台以扩展态承载更多生产状态。

### 2.4 设计即查询/开发

原子指标定义完成后，即同时具备业务口径（口径层）与算法实现（算法层），可直接被派生指标引用、直接生成查询 SQL 或驱动汇总表开发。**设计即查询/开发**是原子指标的核心设计原则：定义即消费，口径层回答业务语义，算法层回答怎么算。

### 2.5 以上也要维护

三层配置（基础信息、计算口径、业务信息）都需维护，且必须同步：

- 口径变更：走业务口径评审，更新基础信息
- 算法变更：评估下游派生/复合指标影响，更新计算口径
- 治理变更：负责人变更、状态流转（新建→已发布→已修改→已下线）按生命周期规范维护
- 三层同步更新，禁止只改一层导致口径与实现不一致

## 3. 派生指标设计

派生指标按**配置分层**组织，与原子指标一致：**基础信息（口径层）**、**口径配置（派生逻辑层）** 与 **业务信息（治理层）**。

### 3.1 基础信息——口径层

与原子指标基础信息相同（9 项），另增**指标备注**。度量格式/度量单位/小数位数/源头系统默认继承依赖指标（原子或派生），仅在需要时覆盖。

| 配置项 | 必填 | 配置说明 | 填写规范 | 示例 |
|---|---|---|---|---|
| 英文名称 | 是 | 派生指标唯一标识 | 由"业务限定前缀 + 原子英文名"构成，小写+下划线、全局唯一，符合附录 B 命名规范 | `special_cancer_occur_amt` |
| 数据域 | 是 | 指标归属分析主题域 | 默认继承依赖指标的数据域 | 结算费用域 |
| 中文名称 | 是 | 业务可读主名称 | 与英文名称一一对应，同主题域内不重复 | 门特-癌症-发生金额 |
| 度量格式 | 是 | 展示类别 | 默认继承依赖指标，需要时覆盖 | 金额 |
| 度量单位 | 是 | 计量单位 | 默认继承依赖指标，需要时覆盖 | 元 |
| 小数位数 | 金额/比率必填 | 展示精度 | 默认继承依赖指标，需要时覆盖 | 2 |
| 源头系统 | 否（建议填） | 业务溯源 | 默认继承依赖指标，需要时覆盖 | 银海his,天信his |
| 同义词 | 否 | 业务别名 | 逗号分隔，供检索匹配 | 门特癌症费用 |
| 指标描述 | 否 | 用途与适用场景 | 回答"用来做什么" | 用于分析门特渠道费用结构 |
| 指标备注 | 否 | 口径注意事项/计算规则/引用出处 | 与指标描述分工：备注写"怎么算、有什么坑、依据什么" | 仅限门特待遇，非普通门诊 |

### 3.2 口径配置——派生逻辑层

回答"这个派生指标如何从基础指标圈定/计算出来"。不同指标类型的必填配置项不同（见下表）。

| 配置项 | 必填 | 配置说明 | 填写规范 | 示例 |
|---|---|---|---|---|
| 指标类型 | 是 | 派生形态分类 | 枚举：筛选型 / 累积计算型 / 同环比计算型 / 混合计算型 / 转化计算型；各类型专属配置见下表 | 筛选型 |
| 依赖指标 | 是 | 派生所依赖的基础指标 | 支持原子或派生指标；优先依赖原子（链尽量扁平）；同算法复用不新增；禁止循环依赖；**当前按序列号引用，注意跨层序列号歧义**（如 1 既可能是原子 1 `settle_amt` 也可能是派生 1 `total_occur_amt`），规划改英文名称主键 | `occur_amt` 或 `special_cancer_occur_amt` |
| 业务限定 | 筛选型/累积计算型必填 | 业务场景圈定 | 渠道/病种/机构等场景条件，不含时间区间；与原子层过滤条件（数据有效性）区分 | `treat_type=门特, fee_category=癌症` |
| 业务口径 | 是 | 一句话业务口径（口径定义） | 不含表名/物理字段名；四方评审必读字段；保留在口径配置区 | 门特渠道癌症病种的发生金额 |
| 限定口径 | 否 | 业务限定的展开说明 | 可写具体条件表达式 | `treat_type_name='门特' and fee_category_name='癌症'` |
| 支持统计周期 | 累积/同环比计算型必填 | 可用的统计周期 | 日/月/季/年，逗号分隔 | 月,季,年 |
| 计算逻辑 | 同环比/混合/转化计算型必填 | 派生计算表达式 | 筛选/累积默认继承依赖指标算法；混合/同环比/转化填写公式或增长率 | `sum(...)`、`A - B`、环比增长率 |
| 技术口径(源业务库口径) | 否 | 开发提供的源业务库口径 SQL | 与原子指标一致，可含表与字段 | `select sum(amt) ... where ...` |
| 挂载数据集 | 只读 | 派生指标落地的数据表 | 由数据集页面配置维护，派生指标页只读展示；统计粒度=表粒度，粒度不进指标定义 | `wedw_dws.settle_surplus_hospital_month_stat_df` |

**按指标类型的专属配置**：

| 指标类型 | 依赖指标 | 专属配置项 | 示例 |
|---|---|---|---|
| 筛选型 | 1 个（原子或派生） | 业务限定 | 门特-癌症-发生金额 |
| 累积计算型 | 1 个 | 业务限定 + 支持统计周期 | 年度累计发生金额（YTD） |
| 同环比计算型 | 1 个累积计算型派生 | 计算逻辑（同比增长率 / 环比增长率） | 近30天线上金额环比增长率 |
| 混合计算型 | 多个 | 计算逻辑（公式 A-B、A/B） | 结余金额 = 人头总额 - 支付金额 |
| 转化计算型 | 初始事件指标 + 转化事件指标 | 计算逻辑（转化率 / 转化值）+ 链接字段 + 转化窗口 | 注册-下单转化率 |

### 3.3 业务信息——治理层

与原子指标一致，另增术语标签。

| 配置项 | 必填 | 配置说明 | 填写规范 | 示例 |
|---|---|---|---|---|
| 创建人 | 是 | 指标录入人员 | 记录指标录入者；系统自动带出当前登录人，不可手动修改 | wangyn3 |
| 业务负责人 | 是 | 业务方 | 指标口径变更的评审联系人，负责业务口径确认 | 张三 |

## 4. 复合指标设计

复合指标的三层结构与派生指标一致：**基础信息（口径层）**、**口径配置（复合逻辑层）** 与 **业务信息（治理层）**。

### 4.1 基础信息——口径层

与派生指标页面形态一致，但**字段保持复合专属**（不含度量格式/度量单位/小数位数/源头系统/指标备注），共 6 项：数据域、英文名称、中文名称、同义词、指标描述。详情页见 `composite-detail.html`，字段规格与 v3.0 4.3 一致。

### 4.2 口径配置——复合逻辑层

复合指标 = 多个派生指标的公式组合。口径配置为简化版，仅保留复合必需项。

| 配置项 | 必填 | 配置说明 | 填写规范 | 示例 |
|---|---|---|---|---|
| 依赖派生指标 | 是 | 公式引用的派生指标集合 | 多个，逗号分隔；按英文名称引用（当前按序列号，规划改英文名称主键）；禁止循环依赖 | `surplus_amount,sab_head_amount` |
| 公式 | 是 | 复合计算表达式 | 仅引用派生指标英文名称与四则运算/括号，禁止裸表字段 | `surplus_amount / sab_head_amount` |

说明：复合指标**不配置**指标类型、业务限定、限定口径、支持统计周期、时间字段、技术口径、挂载数据集（由依赖的派生指标承载；挂载数据集默认不配置，在 opendata/BI 层实时计算，确需物化时由数据集页配置）。

### 4.3 业务信息——治理层

与派生指标 3.3 完全相同（创建人、业务负责人、产品负责人、技术口径负责人、状态、术语标签）。

## 5. 界限判定

### 5.1 一句话判据

- 原子指标回答"算的是什么"（算法抽象）
- 派生指标回答"在什么范围、什么周期内算"
- 复合指标回答"已算好的指标值之间如何再运算"

### 5.2 三条硬边界

1. **输入类型不同**：筛选型/累积计算型派生的输入是"明细数据 + 过滤条件"；混合计算型派生与复合指标的输入是"已定义的指标值"（公式组合）。两者的区分在落地形态：混合计算型派生通常落地 dws 物理字段，复合指标默认在 opendata/BI 层实时计算。
2. **是否新增业务语义不同**：派生指标新增"场景圈定"（where 条件、时间窗口），不改变算法本身；复合指标新增"指标间关系"，本身不含业务限定。判定方法：去掉限定和周期后算法仍完整自洽 → 派生；去掉公式后什么都不剩 → 复合。
3. **属性归属不同**：可累加/半累加/不可累加、窗口取值、时间标识属**原子层**；统计周期、业务限定属**派生层**；统计粒度属**挂载层**（由挂载表/数据集决定，不属于任何指标层）。

### 5.3 三步判定流程

对任意新指标依次回答：

1. 能否脱离业务场景单独定义算法？能 → **原子**（同算法跨表复用，不重复新增）。
2. 是否 = 某个原子 + 业务限定 + 统计周期？是 → **派生**。
3. 是否引用两个以上已定义指标做运算？是 → **复合**。

以上都不满足时，检查的是挂载表和粒度归属问题，而不是分层问题。

> **平台实现说明（粒度下沉挂载实体）**：Unisense 按本界限落地时，`metric` 主表
> 不再承载粒度——派生指标的源表/源列/粒度/默认周期下沉到独立挂载实体
> `metric_mount`（一个派生指标一个挂载点），原子指标通过 `measure_id` 关联
> 逻辑度量目录 `measure_catalog`（度量格式/默认单位/小数位/源头系统/同义词），
> 不直接绑定物理表。粒度口径以挂载实体为准（`metric.granularity` 仅保留兼容冗余）。

## 6. 易混点

- **A/B 类公式组合的归属看落地形态**：混合计算型派生（如结余金额 = 人头总额 - 支付金额）是重要基础指标、落地 dws；复合指标（比率/占比/同环比/转化率）默认在 opendata/BI 层实时计算、不落 dws。
- **筛选型派生与复合的区别**：筛选型派生只是给原子加限定（如渠道=线上），结果仍是单值聚合；复合是多个指标的公式组合，本身不含业务限定。
- **粒度不属于任何指标层**：同一算法可挂不同粒度的数据集，粒度由挂载表自身决定，不写入指标名称与定义。
- **原子层不做二次组合**：混合运算（A-B、A/B）在派生层（混合计算型）或复合指标层完成，原子指标仅承载单一算法抽象，不做公式组合。
- **同环比/转化计算型是派生指标类型**：同环比（如环比增长率 = (A − 上周A) / 上周A）依赖 1 个累积计算型派生指标，属派生层；复合指标是面向消费的公式配置（默认实时计算）。
- **总/总数 ≠ avg(字段)**：人均人头总额（`总额/总数`）是复合；`avg(明细字段)` 是对明细记录取平均，属原子/派生，两者业务含义不同，不可混用。

## 7. 实例（取自知识库真实数据）

### 7.1 三层递进示例

以结余分析链路为例：

| 层次 | 中文名 | 英文名 | 相比上一层的增量 |
|---|---|---|---|
| 原子 | 发生金额 | `occur_amt` | 算法：sum（来源参考 `wedw_dw.settle_surplus_summary_detail_df`；历史遗留名，新指标统一 `_settle_amt` 后缀） |
| 派生 | 门特-癌症-发生金额 | `special_cancer_occur_amt` | 依赖 `occur_amt`，加业务限定 `treat_type=门特, fee_category=癌症`，支持统计周期 月/季/年 |
| 复合 | 结余率 | `surplus_rate` | 公式：`surplus_amount / sab_head_amount`（依赖结余金额、人头总额两个派生指标） |

其他原子示例：`settle_amt`（结算金额，SUM 聚合，被 `total_amt`/`settle_total_amt`/`his_total_amt` 等派生指标依赖）；`settle_expense_patient_cnt`（发生费用患者数，count distinct）。

### 7.2 边界判定示例（判定法应用）

对 3.2 判据（"去掉限定和周期后算法仍完整自洽 → 派生；去掉公式后什么都不剩 → 复合"）的实例验证：

**派生示例：门特-癌症-发生金额**

- 定义：`occur_amt`（sum 发生金额）+ 业务限定（`treat_type=门特, fee_category=癌症`）+ 统计周期（月）
- 判定：去掉限定和周期后剩 `sum(发生金额)`，算法完整自洽 → 派生

**复合示例 1：人均人头总额（总/总数 ≠ avg(字段)）**

- 定义：`avg_head_amount = sab_head_amount / contract_count`，除号两边均为已定义派生指标值，不再触碰明细
- 判定：去掉公式后什么都不剩 → 复合
- 易混：若写成 `avg(人头总额)`，是对"每条明细记录的人头总额取平均"，业务含义完全不同。`总额/总数` 与 `avg(明细字段)` 是两回事：前者是复合，后者属原子/派生

**复合示例 2：单输入的同环比也是复合**

- 定义：环比增长率 = (A − 上周A) / 上周A，仅依赖一个指标 A
- 判定：虽然只有一个输入指标，但属于"指标值之间的运算"，去掉公式后什么都不剩 → 复合
- 对比：近 30 天线上渠道交易总金额 = 交易总金额（原子）+ 业务限定（渠道=线上）+ 统计周期（近30天），去掉限定和周期后剩 `sum(金额)` → 派生

**复合示例 3：公式中的裸表字段反例**

- 若把"结算金额占人头总额的比例"直接写成 `金额 / 人头总额`（两边为明细表字段），按 3.2 判据看似复合，但不是合法复合指标：复合指标公式仅允许引用已定义派生指标与四则运算/括号，禁止裸表字段（见 1.2）
- 正确做法：先定义两个派生指标（如 `surplus_amount`、`sab_head_amount`），再做组合

### 7.3 属性归属示例

- **半累加属原子层**：每日库存快照或"月末在管患者数"在时间维度上不可累加，需在原子指标上配置窗口取值（最新值/最旧值），如月末库存取每月最后一天的库存值；派生指标只继承该属性，不重复声明。
- **粒度属挂载层**：如 `wedw_dws.settle_surplus_hospital_month_stat_df` 为机构月粒度、`wedw_dws.settle_surplus_area_payment_month_stat_df` 为区域月粒度，同一算法可挂不同粒度数据集，粒度不进入指标定义。
- **去重计数与累加性**：按规格书 v2.0 5.3.3 目标设计，去重计数默认不可累加（带时间窗口取值语义时才用半累加）；存量数据（如 `settle_expense_patient_cnt` 当前记录为可累加）需在数据对齐（规格书附录 E）时统一。
