## 2. 本批补齐项（gap-fill T1–T5）上线风险点与缓解

> 以下按「风险 → 缓解 → 回滚预案」逐项列出。所有新功能应走 feature flag（`backend/app/core/feature_flags.py` FeatureFlagManager 已就绪），实现「一键下线」能力。

### 2.1 T1 检索 synonyms 接线 + 前端联想

- 改动范围：`backend/app/services/global_search/repository.py`（检索路径 MySQL LIKE 追加 synonyms 匹配）；前端顶栏 AutoComplete（Layout.tsx）+ GlobalSearch.tsx「同义词命中」提示。现状：synonyms 字段在 `models/term.py:42` 已存在但检索零匹配。
- 风险：
  - R1.1 检索 SQL 从单条件 LIKE 扩为 `code/name/description/synonyms` 多 OR LIKE，命中索引效率下降，检索响应 P95 退化（现有全局检索为跨 8 类资源聚合）。
  - R1.2 synonyms 命中可能引入噪声（同义不同义、歧义词），「您是不是想找…」提示误导向。
  - R1.3 LIKE 参数化若未正确转义 `%`/`_`，引入通配符注入面（既有 `_escape_like` 须继续用于新增字段）。
- 缓解：
  - 检索保持参数化 + `_escape_like` 转义（对齐既有 2026-08-15 `search_assets` 内存包含匹配避开 `_escape_like` 下划线转义坑的教训）；新增 synonyms 字段复用同一守卫。
  - 对检索结果统一 LIMIT 上限（既有强制 LIMIT 模式），追加同义词匹配不得放大分页深度。
  - 前端联想为纯提示（点击后走正式检索），提示数据失败时静默降级不阻塞主检索。
  - 单测补 synonyms 命中/未命中/转义三用例；前端 vitest 补提示渲染。
- 回滚预案：检索条件恢复为不含 synonyms 的单条件版本（feature flag 关闭）；前端提示组件可独立移除，无数据迁移。

### 2.2 T2 Dashboard 可信度卡 + 详情页信任增强

- 改动范围：Dashboard.tsx 复用 `GET /observability/overview` 已返回的 `quality.metric_health`（by_level+top_risk，observability/repository.py:497-556）渲染红黄绿分布 + Top 风险；MetricDetail.tsx 补「最近一次校验通过时间」（health.calculated_at / 快照 generated_at）与「被多少报表引用」（复用现有血缘下游/impact 接口）＋「一键试算」入口（接入 `/consume/metrics/{code}/query` + QueryWorkspace）。
- 风险：
  - R2.1 metric_health 聚合为实时计算，overview 端点在并发下若有慢聚合，Dashboard 首屏 P95 退化。
  - R2.2 calculated_at/generated_at 可为空（未跑过健康检查/快照），前端若强依赖会渲染异常。
  - R2.3 一键试算直接打 consume 查询端点，若复用现有权限则 OK；但需确认查询的域/ PII 门禁已生效（避免可信度卡片侧漏出越权试算入口）。
- 缓解：
  - 前端按 DEV_GUIDE §8 五态实现（加载→空→正常→错误→降级）：calculated_at 空时展示「暂无校验记录」占位。
  - overview/metric_health 聚合复用既有只读聚合路径，必要时加结果缓存（TTL 对齐 §17.2）。
  - 一键试算复用 consume 既有 RBAC/PII 门禁（内部用户分支已接入 PDP，2026-08-15 治理增强），前端按 `/me/permissions` 收敛入口。
- 回滚预案：纯前端展示层变更，回滚前端静态资源即可；无后端/迁移变更。

### 2.3 T3 统计端点（复用度/资产账本/合规报告/一致率/时效）

- 改动范围：新建 `backend/app/services/analytics/` 只读聚合模块 + 新端点文件 + 前端新页。复用血缘 `DERIVED_FROM/CONSUMED_BY` 边（lineage/schemas.py:340）、HealthScorer 活跃度维度（health_scorer.py:180-195）、audit 审计日志（audit.py:76/137 + metrics.py:224-225 PII 访问审计）做只读聚合。
- 风险：
  - R3.1 审计日志表为大表（WORM 只增），按指标聚合「谁访问过/导出记录」若全表扫描将超时或拖垮写路径；PII 访问明细聚合若口径不严会扩大敏感信息暴露面。
  - R3.2 复用度/资产账本聚合血缘边，扇出大节点（被海量报表引用）聚合响应无上限 → 响应膨胀（对齐 lineage `max_edges=5000` 既有教训）。
  - R3.3 口径一致率/响应时效 KPI 依赖数据模型（glossary/measure_catalog、提数需求记录），若基础数据缺失，端点返回空/误导性结论。
- 缓解：
  - 所有聚合端点强制分页/上限（复用 lineage `max_edges` 模式）；审计聚合先按 `metric_code`/时间窗过滤再聚合，禁止无界全表扫描。
  - 合规报告端点按治理角色收敛（PII 访问/导出明细仅合规/管理角色可读，对齐 `_PII_READ_ROLES`），并写 `pii_access` 审计（列表类暴露同 PII 列表审计模式）。
  - 时效 KPI 在 docs 说明数据假设（基于 consume/query 日志最小可行统计），空数据时返回空数组 + 提示，不编造。
- 回滚预案：新端点独立 feature flag；下架时前端入口移除 + 端点 404（无迁移依赖）。若引入新表，须带可逆迁移。

### 2.4 T4 质量对账定时调度 + 词根硬校验 + 术语强制

- 改动范围：`quality/tasks.py` 加定时 reconcile 调度（外部基准对账 import→bind→run→confirm 现有链路 quality/service.py:592-721，支持自动抽样基准）；`semantic/conflict_precheck.py:36-123` 词根/词素字典服务端硬校验（现有 4 段格式正则+保留词软提醒）；`semantic/repository.py` 指标创建强制校验引用术语（复用 bind_metric_term 链路）。
- 风险：
  - R4.1 定时对账任务在 arq worker 中跑，若对账 SQL 扫大表/外部基准大，任务超时或与其它定时任务争抢 worker。
  - R4.2 自动抽样基准可能因抽样窗口数据波动误报质量事件，产生告警疲劳。
  - R4.3 词根硬校验/术语强制新增在**创建/发布**路径，存量指标或未绑定术语的合法创建将被新规则拦截 → 上线后创建失败率跳升（此前 2026-08-13 曾发生迁移 0025/0026 空表致存量创建全阻断的教训）。
  - R4.4 端到端「源表 DDL→受影响指标→Owner 通知」链路依赖 collector schema drift + notify 定向通知，跨服务断点会导致整链静默失败。
- 缓解：
  - 对账调度：cron/间隔可配置 + 默认低频（如每日非高峰）；抽样设上限与超时（对齐 collector 采集 `asyncio.timeout(300)` 模式）；对账只生成差异列表不自动写业务数据，误报仅影响报告。
  - 硬校验：词根/术语强制先软提醒 → 阈值/开关可配置，且**仅对新创建/新发布生效**，存量不受影响；错误信息带规范提示（对齐既有 4 段格式校验的报错体验）。
  - E2E 用例落 `tests/`（参照 test_lineage_* 与 integration 既有用例），覆盖「源表 DDL→受影响指标→Owner 通知」整链，mock 仅外部依赖。
- 回滚预案：调度任务开关关闭即停；硬校验开关关闭回退软提醒；无数据迁移。

### 2.5 T5 治理域：批量迁移 + 僵尸下线审批流 + 按资产订阅 + 质疑闭环

- 改动范围：批量迁移端点（生成逻辑度量 measure_catalog + 挂载 metric_mount）；`semantic/service.py:2392-2501` deprecate 增加「被引用则拦截」+ 可选 admin/owner 双确认审批流；`notify/service.py:941` 订阅增加按资产（指标/源表）粒度（schemas.py:122-128）；feedback 状态机扩展「质疑→澄清→修订」。
- 风险：
  - R5.1 批量迁移（批量生成度量+挂载）事务边界：部分失败污染已成功项 → 须逐条容错 + 审计区分部分失败（复用 `_run_batch` 模式，batch 端点 207 语义）。
  - R5.2 deprecate 被引用拦截：存量指标已被引用（消费方在用），硬拦截导致合法下线流程卡死；审批流双确认若通知链路断，审批悬置。
  - R5.3 按资产订阅扩展订阅粒度：扇出逻辑需按 asset 匹配，事件类型与 asset 维度组合逻辑复杂 → 匹配错误导致通知发错人/漏发（对齐 2026-08-15 conflict 定向通知「仅走 HTTP 通道」误判教训）。
  - R5.4 feedback 状态机扩展：旧状态（in_progress/adopted/rejected）与新状态迁移兼容性，历史数据展示。
- 缓解：
  - 批量迁移复用 `_run_batch`（SQLAlchemyError 回滚会话 + 逐条容错 + 部分失败审计），单条失败不污染已成功。
  - 被引用拦截设计为「可强制 + 解引用引导」：报错列出引用方（替代指标/解引用路径），紧急场景保留管理角色强制下线（对齐灰度回收/紧急发布既有模式）；审批流复用现有 approve/reject 状态机 + 审批超时提醒（对齐 conflict SLA 7 天升级）。
  - 按资产订阅：asset 维度白名单校验 + 兼容旧事件类型订阅；订阅 upsert 幂等；扇出走既有 EventBus + notify 三渠道（对齐 notify runbook）。
  - feedback 状态机迁移兼容旧状态，新增状态只前进不破坏既有流转。
- 回滚预案：批量迁移端点/拦截逻辑/订阅 asset 维度各独立 feature flag；订阅 schema 扩展为可选字段（向后兼容），回滚不改表结构；审批流回退单确认。

## 4. 发布与回滚预案

### 4.1 发布顺序

1. 后端迁移（如有新表）`alembic upgrade head`，先 staging 验证可逆（`downgrade -1` 复验）。
2. 后端代码发布（灰度/滚动），feature flag 默认关闭。
3. 观察 24h 指标无退化后，逐个打开 feature flag（先读功能、后写功能）。
4. 前端静态资源发布（版本化），配合 flag 渐进放开入口。

### 4.2 回滚触发条件

- P95 较基线（131.63ms / 各 perf_contract）退化 > 20%，或失败率 > 0.5%。
- 指标创建/发布失败率显著上升（怀疑词根硬校验/术语强制误拦）。
- 对账任务误报率突增（怀疑抽样基准问题）。
- 检索/统计端点 5xx 或慢查询打满。

### 4.3 回滚手段（按层级）

| 层级 | 手段 |
|------|------|
| 功能级 | feature flag 关闭（新检索条件/硬校验/调度/批量端点/订阅粒度，逐项独立） |
| 应用级 | `kubectl rollout undo deploy/unisense-api`（semantic runbook §5 既有） |
| 数据级 | `alembic downgrade -1`（各 runbook 迁移可逆已复验；仅结构回退需评估审计影响） |
| 前端 | 回退静态资源版本（纯展示层变更无迁移） |
